## 写在前面

我们每天接触大量文档、会议、表格和消息。一项工作经常要经过查找、理解、比较、表达和交接，才能被另一个人继续使用。办公 Agent 带来的一个机会，是让这些步骤能够围绕明确的目标组织起来，成为可以共同完成和检查的任务。

本书先从普通工作者熟悉的场景开始。怎样选择一个值得尝试的任务，准备必要的信息，把要求交代清楚，再判断交付是否可靠？第一篇围绕这些问题展开，其中一章提供了可复现的模拟练习。

当越来越多的人开始采用相近的方法，新的问题也会出现。资料有多个版本，业务口径没有统一，经验保存在个人聊天里，工作仍然卡在交接处。第二篇因此把重点放在组织共同能力上：共建知识，按任务提供上下文，连接系统和工具，调整流程、分工与评价。

第三篇再把视野推向企业集团、经营与生产、供应链和行业，以及知识获取、劳动和价值创造方式的变化。这些影响需要经过具体机制才能发生，也需要参与者作出选择。本书保持积极建设的视角，讨论我们可以怎样参与其中。

你可以从头阅读，也可以根据职责进入相应章节。个人使用者先看第一篇；团队与数字化工作的参与者可以重点阅读第二篇；企业管理者和关心工作变化的读者，可以结合第三篇再回看实践基础。书末提供了几份简短的工作模板，供实际使用时调整。

书中的证据分为几个层次。第 3 章的项目材料是原创模拟资料，Agent 确实据此生成了本地交付文件，读者可以逐项核对。后续的团队、集团和行业情境主要用于说明设计与推演，均标明其性质。引用的产品资料和研究，只支持相应范围的判断，不替代具体工作中的验证。

全书要回答的，是一个逐渐展开的问题：个人怎样用好 Agent，一群人怎样形成共同能力，而我们又希望这些能力把工作与生活带向哪里？

## 第一篇 从个人任务开始改善工作

先从手边的一项工作开始：它需要哪些材料，谁会使用成果，做到什么程度才算完成？这些问题能帮助我们看清 Agent 可以承担的步骤，也帮助我们保留必要的判断。

这一篇依次讨论工作方式、任务准备、实际交付和结果复盘。个人经验怎样进一步成为组织共同能力，将从这里展开。

## 第 1 章 Agent 怎样参与我的工作

### 把一项工作交出去

先设想一个常见情境：会议结束，你需要更新一份项目说明，供同事第二天讨论。手边有会议记录、上一版文档和一张进展表。你可以请 AI 帮忙改几句话，也可以逐段复制材料，让它依次整理。

做着做着，你会发现，文字只占工作的一部分。还要找到这次修改涉及哪些段落，区分已经形成的决定和仍在讨论的建议，检查表格中的进展是否影响说明，最后保存一份别人能够接着使用的文件。

如果希望把这些步骤一起交给 AI，就需要说清整项工作：依据哪些材料，更新到什么程度，遇到不确定的内容怎样处理，完成后交付什么。Agent 正是在这样的任务中参与进来。

本书把 Agent 理解为能够围绕目标，借助可用工具选择并推进若干步骤的 AI 系统；这种工作方式也见于 [OpenAI 的 Agent 使用指南](https://learn.chatgpt.com/docs/working-with-agents)。接下来，我们沿着这份假设的项目说明，看它怎样开展工作。

### 它依据什么开展工作

一项任务交到 Agent 面前，并不意味着它已经了解你的工作。你说“更新项目说明”，它还需要知道哪份是当前版本、哪些讨论已经生效、文件将供谁使用。这些信息共同影响它能作出的判断。

我们把当前任务中可供它使用的相关信息称为上下文。其中可以有目标、材料、角色、规则和已有记录，也有执行过程中取得的新信息。[Anthropic 的上下文工程说明](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)将指令、工具相关信息、外部资料和历史消息等放在一起讨论。本书会先从你每天接触的工作材料解释它。

模型提供理解、生成和推理等能力。它可以分析会议讨论涉及哪些问题，组织说明的表达，提出下一步应检查什么。可是，会议上没有明确的结论，仍然可能没有明确的结论；文件里缺少的批准记录，也需要继续查找或向人确认。

工具让任务能够接触实际资料并采取行动。读取文件、检索内容、进行计算、保存新文档，都需要对应的能力可用。工具的用途和操作条件帮助 Agent 判断怎样使用它，真正能否执行，还取决于接口、权限和运行环境。

因此，选择工具时值得问得具体一些：它能否读取这份文档？能否看到需要的表格内容？修改后能否留下可检查的文件？这些条件会直接影响任务能交到哪一步。仅在对话里生成了一段修订建议，与已经保存了一份修改后的文档，是两种不同的交付。

### 怎样一步步接近目标

沿着项目说明的例子，Agent 可以先读取会议记录和旧文档，找出需要更新的部分。若记录中提到一项新的安排，它还可能需要检查相关进展，再决定这项安排应写成确定事项还是待讨论内容。

一次处理的结果，会影响下一步。找到的材料足够清楚，可以继续写入草稿；材料相互矛盾，可以先列出差异；缺少决定性的输入，可以停在问题清单上，等你补充。

这个过程可以简单画成：

```text
理解目标与约定 → 读取材料 → 判断下一步
使用工具处理 → 检查结果
需要调整：补充信息或改变步骤，继续执行
达到约定：形成交付物
```

图里的检查有不同层次。Agent 可以检查要求的章节是否齐全、文件是否生成，也可以按约定回查来源。人还要判断这份说明是否足以支持讨论，其中涉及业务取舍的表述是否恰当。

你不必从它说了多少句话来判断进展。更有用的线索是：读了哪些材料，形成了什么文件，哪些问题已经处理，哪些仍然卡着。如果它只说“已经全部完成”，你仍需要打开成果，看它是否符合交付要求。

### 聊天、流程与 Agent 可以怎样配合

在实际使用中，这几种方式可以放在一起。你通过聊天讨论目标，再启动一项有固定步骤的处理任务；其中某个环节，又由 Agent 根据材料决定接下来查询什么。

例如，项目说明中一句话不够清楚，几轮对话就可能帮助你找到合适表达。每次收集材料都要按相同规则归档，固定流程可以承担这段稳定工作。至于不同会议涉及不同问题、需要临时查找依据的修订，适合进一步考虑由 Agent 组织处理步骤。

所以，界面上看见一个聊天框，不能据此判断它只会回答问题；产品写着 Agent，也仍要看它在当前任务中实际具备哪些能力。选择的依据是工作需要怎样推进，以及结果怎样检查。

步骤能够自行调整，意味着你可以少安排一些具体操作，也意味着需要把范围和完成标准交代清楚。一个很小的修改，如果交付要求已经明确，就不必为了使用更多能力而扩大任务。

### 人的判断放在哪里

把执行交出去之后，你的判断会更多地集中在目标、取舍和验收上。这份项目说明是为了统一已有安排，还是帮助大家比较不同方案？哪些内容可以直接修改，哪些需要保留不同意见？这些选择会改变成果的写法，也会改变它在工作中的作用。

执行中，你也可以根据进展调整要求。发现它花了很多篇幅润色背景，却没有交代新的行动事项，就应把注意力拉回需要支持的决定。发现关键材料缺失，可以缩小范围，先完成有依据的部分。

这种参与需要你懂得自己的工作。Agent 可以帮你整理信息和提出选项，使用成果的人仍要辨认哪些说法可靠、哪些决定尚未作出。愿意检查和给出具体反馈，才能逐渐形成适合自己的协作方式。

### 从一件能判断好坏的事开始

初次尝试，可以先选一项范围清楚、材料能够提供、结果也能检查的工作。更新一份短说明、整理一组问题，或者形成一份有来源的任务进展，都可以成为观察协作方式的起点。

先想清楚希望得到什么，再看看自己能否辨认成果的好坏。接着准备必要材料，明确它可以处理到哪里。下一章就从这个选择开始：在你手上的工作中，哪一项值得交给 Agent？

## 第 2 章 选好任务，准备必要的上下文

### 从自己能够判断的成果开始

准备第一次使用 Agent 时，可以先看看今天的待办事项。哪件事需要来回翻资料、比较几个版本，最后形成一份别人会用到的成果？哪件事完成之后，你能说清楚它是否合格？

下面是一个说明例子：你要把三份培训活动方案整理成一页对照材料，供负责人讨论。材料里有对象、安排和预算，但有些信息不完整。你熟悉这项工作，能够检查重要内容有没有遗漏，也知道哪些问题必须问清楚。这样的任务可以作为一个起点。

选择任务时，先找一件材料能够取得、结果能够检查的事。任务即使经常重复，如果每次的资料和判断都不同，也要把这种变化考虑进去。若你暂时无法分辨结果是否正确，可以先请熟悉业务的同事共同确定标准，或者进一步缩小范围。

一个简单的问题，用一次对话就可能解决。已经稳定的固定步骤，也可以沿用原有流程。是否需要 Agent 继续找资料、比较信息、调用工具，要看任务过程中有哪些步骤需要根据发现来调整。先把工作看清楚，才容易判断怎样协作合适。

### 范围可以小，结果要完整

“帮我把这次培训做好”很难成为一次清楚的委托。它包含确定目标、选择内容、安排人员、沟通和执行，其中不少决定还没有形成。

可以先把任务收拢为：根据给定的三份方案，按参加对象、时间安排、预算和准备条件形成对照材料，列出差异与待确认问题，供负责人开会讨论。做到这里，这个任务就有了完整的使用场景。

使用人也会改变成果的写法。给执行同事的材料，需要便于分工和跟进；给负责人讨论的材料，更需要说明差异、依据和仍要决定的事项。把这层用途交代出来，Agent 才有理由判断哪些内容应放在前面，哪些细节可以留在附件中。

### 整理本次需要的上下文

材料准备可以从现有文件开始。把相关方案放在一起，说明它们的版本、来源和统计时点，再补一段背景：为什么要比较，哪些条件已经确定，哪些地方还在讨论。

如果某份方案的预算后来调整过，应指明本次采用哪个版本。若两份记录互相矛盾，也可以一并提供，并要求把差异列出来。选择材料的过程，本身就在整理你希望成果依据什么。

还需要交代那些熟悉业务的人容易省略的规则。例如，本次预算是否包含场地费用，参加对象是否已经确定，某项安排是否必须经过负责人确认。这些规则会影响比较结果，不能靠 Agent 从文件名或日常经验中猜出来。

你可以先准备一个小范围的资料包，完成一项具体任务，再把有效做法留下。组织层面的知识基座，会在多人持续复用、更新和协作时逐渐成为需要解决的问题。第一次尝试，只要把当前任务所依赖的资料与规则整理清楚，就已经可以开始。

### 看看工具实际能够做什么

任务确定以后，再核对你使用的 Agent 能接触哪些材料、执行哪些动作。它能否读取这些文件格式？能否访问资料所在的位置？能否生成并保存你需要的文件？这些条件会影响实际交付。

例如，一份扫描图片中的表格，和一份能够直接读取的文本表格，需要不同的处理能力。如果工具无法读取原材料，可以先取得可用的文字版本，或者把暂时不能处理的部分单独说明。发现缺口之后调整安排，比执行结束才发现缺了一整份资料更容易处理。

业务动作也要交代清楚。本次只生成对照材料供人审阅，还是需要进一步填写系统、发出邀请？如果后续动作需要负责人作出选择，就说明由谁决定、Agent 在什么结果处交回。访问资料的权限和执行操作的权限分别核对，不从“看得到”推定“可以改”。

### 把合格的样子写进委托

交代任务时，可以先用几句话描述目标，再补齐影响结果的条件。[OpenAI 的 Agent 使用指南](https://learn.chatgpt.com/docs/working-with-agents)也建议把任务、上下文、可执行动作与交付要求说明白。下面这份简短委托可以按自己的工作改写。

| 要交代的内容 | 培训方案对照的说明例子 |
| --- | --- |
| 目标与使用人 | 为负责人讨论准备一页对照材料，帮助识别差异与还要问的问题 |
| 材料与时点 | 采用本次提供的三份方案；说明版本，保留来源；后续新增材料另行补充 |
| 判断规则 | 按参加对象、安排、预算和准备条件比较；不同预算口径分别说明 |
| 缺失信息 | 未提供的内容标为待确认；材料有冲突时列出依据，区分事实与整理建议 |
| 交付与动作 | 保存对照草稿和待确认问题到指定位置，供负责人讨论后决定下一步 |
| 合格标准 | 三份方案均有交代，重要差异能回到来源；没有依据的费用或安排不补造 |

这份委托不必每次写得一样长。第一次需要解释的内容较多，之后可以保留共同规则，只更新材料和任务变化。若执行中出现了影响判断的新情况，也可以补充信息，让 Agent 根据新的依据继续处理。

开始之前，再问自己一个具体问题：拿到成果后，我准备怎样使用它？如果答案仍然模糊，往往还需要把目标说得更清楚。清楚的使用场景，会让材料选择、表达方式和验收标准相互对应。

### 把委托带入一次执行

现在，从自己的待办中选一项类似的工作，为它写下用途、材料、规则和交付要求。先检查是否具备所需工具与资料，再开始执行。

下一章会把这件事落到一份完整的周报练习中。届时，我们将实际读取计划、进展和会议记录，看看事先交代的完成口径、时点和缺失处理方式，怎样影响最终成果。

## 第 3 章 串起会议、文档与周报

### 从一项熟悉的工作开始

临近下班，你准备写一份项目周报。计划在一份文档里，进展散落在成员的记录中，今天的会议又讨论了新的问题。每份材料都能读懂，放在一起却出现了麻烦：有人写“已完成”，演示时仍有功能失败；大家说“下周交”，却没有确定由谁负责。

周报写到这里，真正费心的是判断。哪些事情已经完成，哪些只是有人这样报告？一个新日期已经获得认可，还是会上提出的建议？把这些问题弄错，文字越流畅，越容易让人误以为事情已经安排妥当。

本章用一个模拟项目做练习：内部培训报名流程改进。项目、人物和事件均为虚构，材料按真实工作中常见的信息关系设计。我们要根据三份材料，形成截至 2026 年 11 月 6 日 18:00 的周报，并把尚待确认的问题交代清楚。

本次练习需要 Agent 读取本地文件、比较记录、整理判断，再保存交付物。你负责提供任务约定，并判断成果是否适合使用。接下来就沿着这项周报任务，看看准备怎样进入执行。

### 把材料和判断规则一起交出去

练习只有三份原始材料：项目计划、进展记录和演示会议记录。

计划里有五项任务，也有一条很重要的约定：报名表演示版必须同时做到“字段可以提交”和“名单可以导出”，才算通过验收。任务调整期限，需要项目负责人确认。这两条规则会影响整份周报的判断。

进展记录中，开发人员陈屿在 11 月 5 日写下演示版已完成。第二天的会议记录却记载：现场能够提交字段，导出时没有得到名单文件。会上还提出，把验收时间改到 11 月 9 日，但项目负责人赵明未参会，记录中也没有批准意见。

如果只交给 Agent 一句“帮我写得专业一些”，这些区别很容易被藏进整齐的段落。我们需要把希望它遵循的判断规则交代出来。可以这样委托：

```text
请读取本练习 materials 文件夹中的项目计划、进展记录和会议记录，
生成截至 2026-11-06 18:00 的周报。

按计划中的验收口径判断完成情况；保留不同记录之间的冲突。
区分原定期限、建议改期和已批准改期。
负责人或期限缺失时明确标注，不根据发言人或相邻任务补齐。

请交付周报、待确认问题、关键判断的来源对应表，
保存到本练习 results 文件夹。
```

这里交出去的，包含资料、目标、范围和判断标准。它们共同构成当前任务所需的上下文。文件里的业务规则同样重要，因为 Agent 不能凭一个“已完成”就知道你们怎样认定完成。

### 让执行围绕材料展开

这次本地执行中，Agent 读取了任务委托和三份材料，保存了三个交付文件。成果中能看见几个具体处理：它按计划交代了五项任务，把 T01 和 T04 列入有完成依据的事项；对照进展记录 R02、会议记录 M02 与计划 P02，把 T02 保留在尚未通过验收的事项中。

接着，周报分别列出了原定日期与建议改期，待确认问题中列出应向赵明确认的改期事项。对没有负责人的反馈汇总、没有期限的补充说明，也各自留下问题。整理中提出的协调建议被标明为建议，没有写成已完成的分派。

你可以打开实际保存的 [周报](../examples/ch03-weekly-report/results/weekly-report.md)、[待确认问题](../examples/ch03-weekly-report/results/pending-questions.md) 和 [来源对应表](../examples/ch03-weekly-report/results/evidence-map.md)，对照原始材料检查。它们是模拟材料上的一次执行结果，供读者观察方法。

### 几个容易写错的判断

第一处是“完成”的含义。陈屿的进展记录确实写了完成，会议记录也确实写了导出失败。项目计划要求两项功能同时通过，因此截至统计时点，周报应保留尚未达到验收条件的状态，并指出前后记录不一致，需要核对原因。这样，负责人才能决定先排查、再验收，而不是把任务从视野里移走。

第二处是负责人。试用反馈汇总有 11 月 10 日这个期限，但计划和会议都没有确定谁负责。林岚是协调人，也参加了会议，这些身份仍不足以证明她接下了这项任务。周报应明确写“负责人待定”，并把确定负责人列为需要推进的事情。

第三处是期限。周宁负责补充批量导出说明，但会议没有约定提交时间。旁边另一项操作说明的初稿安排在 11 月 9 日，不能把这个日期顺手移过来。两项材料有关联，也仍然可以有各自的交付安排。

交付里的关键内容，压缩后如下。来源编号可以回到练习材料的具体记录。

| 事项 | 当前判断 | 日期性质 | 来源 |
| --- | --- | --- | --- |
| T02 演示版 | 现场导出失败，尚未通过验收；与开发自报不一致 | 原定 11 月 6 日，拟改 11 月 9 日，材料未见批准 | P02、P03、R02、M02、M03 |
| T05 反馈汇总 | 负责人待定，材料未提供汇总进度 | 原定 11 月 10 日 | P03、M04 |
| 批量导出说明 | 周宁负责，独立补充材料 | 期限待确认 | M05 |

这些差异让周报成为下一步工作的依据。保留“待确认”，使需要人来决定的事能够被看见。

### 把成果接回自己的工作

拿到文件之后，可以先沿着最容易影响行动的判断核查：完成状态、期限、负责人。来源对应表的用处，是让你从一句结论回到具体记录，检查 Agent 有没有把事实、建议和猜测混在一起。

例如，[待确认问题](../examples/ch03-weekly-report/results/pending-questions.md)在保留改期背景之后，列出了这样的问题：

> 是否批准将验收时间调整到 11 月 9 日？如批准，新的范围和完成条件有无变化？若未批准，应按什么安排推进？

你可以带着原计划和这条问题向赵明确认。讨论由此落到一个具体决定上，也便于把答复更新到任务记录中。

得到回复后，还要更新任务记录，再修订周报。Agent 可以在你提供回复后继续整理，但组织中的批准需要由相应的人实际作出。一次文件生成完成，整个业务过程可能仍在继续。

你也可以让 Agent 针对某个问题修改，例如：“请把已经确认的事实和需要负责人决定的事项分开，所有拟改期保留原日期。”有具体依据的反馈，更容易让下一版靠近真正的工作要求。

### 一次练习能说明什么

这次练习让我们看见一种可检查的协作方式：把材料与规则交代清楚，让 Agent 完成整理，再沿着关键判断回到来源。它是否适合你的工作，还需要用你的任务和标准检验。

如果想比较效率，应记录整个过程中的人工投入：找材料、交代任务、处理缺失信息、核查和返工。还要比较成果质量。同样一份周报，写得更快但需要重新查一遍，和一次交付就能支持讨论，是不同的结果。

本练习没有测量人工基线、费用或提效比例。开始使用时，更值得保留的是一份简短复盘：哪些信息起了作用，哪种错误最需要检查，下次可以少解释什么。

### 动手做一次

打开 [本章练习包](../examples/ch03-weekly-report/README.md)，先读三份材料，再把任务交给你可使用的 Agent。完成后，挑出一个状态、一个日期和一个负责人，逐项回到来源核对。

先保存这次的委托、材料和判断。下一章继续考察怎样验收成果、针对问题修订，并把有效经验沉淀下来。

## 第 4 章 检查结果，沉淀自己的工作方法

### 文件已经生成，工作走到了哪一步

你打开 Agent 交来的周报，标题齐全，语句通顺，待办事项也排得整整齐齐。此时最有用的动作，是拿出开始时的任务约定，看看这份成果已经支持你做什么。

如果任务是整理项目状态，那么状态是否有依据，决定了周报能否被采用。如果任务还包括向负责人确认改期，那么生成一条待确认问题，只完成了其中一个环节。询问是否发出、答复是否收到、决定是否写回任务记录，需要分别核实。

上一章的练习范围很清楚：根据给定材料形成三个本地文件。交付达到了这个范围，项目中那些尚未决定的事项仍然存在。理解这个区别，可以帮助你对 Agent 的成果作出恰当评价，也让后续工作接得上。

### 沿着重要判断回看证据

检查可以从最影响下一步行动的结论开始。一个完成状态、一个交付期限、一个负责人，往往比段落是否顺口更值得先看。

周报练习里，T04 试用问题清单已经登记完成，但清单中的导出故障还没有得到修复记录。两句话并不矛盾：登记是一项工作，解决问题是另一项工作。如果报告把两者合并成“试用问题已经解决”，后续安排就可能建立在错误的前提上。

你可以从报告中的判断回到对应记录，再看记录是否足以支持这句话。必要时继续核对状态产生的时间、适用范围和完成条件。来源表能缩短查找路径，判断仍要由你结合任务要求作出。

检查也应覆盖遗漏。逐句核对已有内容，无法发现整项任务没有被写入。原计划有五项任务，交付就需要交代它们各自处于什么状态；临时讨论的独立补充材料，也应有相应位置。对照任务清单查看覆盖范围，是另一种检查方法。

### 让修改针对已经发现的问题

发现错误时，可以先区分问题发生在哪里：材料本身有冲突，任务约定不够清楚，工具没有取得必要信息，还是输出把已有依据整理错了。原因不同，修订的办法也不同。

下面是一个假设的修订情境：另一版周报把 11 月 9 日写成已批准的新验收日期。你可以指出会议记录 M03 只载明改期建议，再要求保留原定日期、标出建议日期，并把是否批准放入待确认事项。这个反馈提供了依据，也说明了合格结果应是什么样。

如果材料里缺少批准意见，反复要求 Agent“再确认一下”并不会产生真实答复。此时应由适当的人取得决定，再将新信息交给它处理。若问题是无法打开某份文件，则需要先解决访问或格式问题，或重新提供可读取的资料。

修改后，既要看被指出的问题，也要看相邻内容有没有受到影响。期限变了，下一步安排可能需要同步；负责人确定了，待确认列表与周报正文也应一致。已有正确内容应保留下来，避免一次局部修订带来更多变化。

### 算清整个任务的投入

判断是否值得继续使用，可以从一项相近、可比较的任务开始。采用同样的交付要求，分别记录原来的做法和与 Agent 协作的做法，再比较人工投入、交付周期和结果质量。

| 记录什么 | 为什么要记录 |
| --- | --- |
| 寻找和准备材料的人工时间 | 看任务是否把大量工作留在执行之前 |
| 交代任务、补充信息和干预的时间 | 看协作本身需要多少投入 |
| 检查、修订和返工的时间 | 看生成后还有多少工作要完成 |
| 从开始到交付的实际周期 | 看等待、重试与交接是否影响推进 |
| 同一标准下的错误、遗漏与可用程度 | 避免把较低要求的成果当作提效 |
| 实际的工具费用与持续维护投入 | 看方法在重复使用时是否值得保留 |

首次建立委托和检查办法的投入，与后续重复使用的投入应分开看。资料发生变化时，维护成本也要记下来。只有记录足够接近自己的工作，比较才有意义。

有些价值也不能仅用省下几分钟表达。例如，报告让一个长期未明确的负责人被及时看见，讨论因此更容易推进。这可以作为具体的观察记录。是否改变了最终交付，还要继续跟踪，不能把一次感受直接写成确定的业务收益。

上一章的模拟练习没有可比的人工耗时和费用记录，因此这里不计算提效比例。你可以借用这张记录表，为自己的下一次使用保留依据。

### 把一次经验变成下次可用的方法

完成一项工作后，值得留下的内容包括：任务要解决什么问题，哪些材料和规则起了作用，哪些判断需要重点检查，以及成果适合怎样的使用场景。

一份周报模板只保留了外形。把“演示版要同时通过提交和导出两项验收”这条规则也留下来，下次整理状态时才有判断依据。把“负责人缺失时不得按参会身份补齐”写进工作说明，则能保留这次发现的一个易错点。

可复用说明应有来源、适用范围和更新线索。它适用于哪类项目，使用哪种完成口径，业务规则变化后谁来确认，都可以用简短的话写清楚。下次沿用之前，再检查材料和要求有没有变化。

复盘可以很轻：留下一个有效做法、一个需要改进的问题和下一次准备怎样调整。随着任务反复发生，再把真正有用的内容整理出来。

### 从个人方法走向共同方法

一个组织问题会逐渐出现：如果每位同事都拿着不同版本的计划，各自定义“完成”，各自在聊天里记下负责人变更，那么每个人都可能生成一份看起来合理的周报，团队仍要花时间解释差异。

需要共同维护的东西也由此清楚起来：一份可信的任务状态、大家认可的验收口径、能够查到的批准记录，以及知识发生变化时由谁更新。这些内容让不同的人和 Agent 可以围绕同一项工作取得相关信息。

共享上下文可以从这些具体安排开始。技术上，上下文还包括指令、工具说明与执行中得到的信息；[Anthropic 的上下文工程说明](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)讨论了这些信息怎样一起组织。到了组织中，我们还要回答一个持续的问题：共同依赖的知识，由谁维护，怎样保持可用？

当同事想沿用你的办法时，可以先从一项任务、一组材料和一份说明开始。一起核对术语、来源和完成标准，观察不同人是否能够理解并采用；发现差异后，修改共同说明。

这时，你留下的经验开始承担新的职责：让另一个人不必重新猜测背景，也能在相近条件下把工作做好。与此同时，知识的负责人、版本、访问范围和更新方式，逐渐成为团队需要共同处理的事。

第一篇建立的是个人与 Agent 协作的起点：理解工作方式，选好任务，准备上下文，完成交付，再用证据和结果判断价值。进入第二篇，我们要把目光移到多人之间：怎样共同建设知识，让不同的人和 Agent 能够围绕同一项工作协作。

## 第二篇 让个人能力成为组织共同能力

个人留下的方法，只有能够被别人理解、采用和更新，才有机会成为共同能力。本篇从交接中的等待与歧义开始，依次讨论知识共建、持续维护、工具执行、流程分工与试点评价，让组织改善落到具体安排上。

## 第 5 章 为什么个人更快，组织仍可能更慢

### 几份文件写好了，项目还没有往前走

周报整理完，林岚仍需要确认改期；操作说明已经有了结构，周宁仍在等待名单导出的验证结果。这是第 3 章模拟材料留给我们的实际关系。Agent 可以帮助个人把问题写清楚，却不能仅靠写出一份文件，就让另一个人作出决定，或让前一道任务达到交付条件。

假设这个模拟团队的每位成员都开始使用 Agent。开发人员更快整理进展，协调人更快形成周报，编写说明的人更快完成文字。这个设想听起来很有希望，但项目何时能够交付，还取决于这些成果能否接起来。如果周报发出后没人处理待确认事项，或说明初稿依据了尚未验证的功能，局部加快仍可能留下同样的等待，甚至增加核对与返工。

组织的速度因此需要沿着一项成果走到被采用的过程观察。一个人完成写作，通常只是下一段工作的开始。

### 同一句“完成”，进入了不同的工作

模拟项目里，开发记录称 T02 的提交和导出均可用，现场记录却显示导出失败。这首先是需要回查的状态差异，材料不能说明差异的原因。

除此之外，组织中还可能出现另一类问题。用一个说明情境看：“完成”对开发者表示准备参加演示，对说明编写者表示功能可以据此介绍，对负责人又表示任务可以关闭。词相同，后续行动不同，误会就在交接时发生。这种口径差异值得单独处理，不能拿它代替对原案例冲突原因的核实。

材料已经提供了解决这个判断的依据：项目计划要求字段提交和名单导出同时通过验收，开发自报与验收通过分别记录。问题在于，每个人的工作是否都能接触到并采用这条口径。把同一条规则分别贴进许多提示词，暂时可以提醒使用者；规则有变化时，又会出现许多需要逐一更新的副本。

状态冲突也不能简单地靠选取最后一条消息解决。时间较晚的记录有可能只是转述，较早的制度仍可能有效。需要比较的是记录说明了什么、由谁确认、适用于哪个时间点。Agent 能帮助把冲突找出来，负责判断的人仍要有明确依据。否则，越来越快的生成只会让多个版本更快流向下游。

### 沿着交付画一张图

要找到真正的阻碍，可以先不讨论给多少岗位配工具，而是请相关人员一起把一项交付的去向画出来。以下是围绕模拟项目作的流程设计延展，箭头表示信息和工作依赖，并不代表新增安排已经发生：

```text
排查并验证导出 → 更新任务状态 → 补充相关说明
审阅说明 → 用于培训
期限调整：由负责人确认后更新计划

试用问题登记 → 明确汇总负责人 → 汇总反馈 → 决定后续处理
```

图画得简单，讨论却要落到每个箭头上。接收人需要什么，才愿意开始？发送人怎样知道对方已经接手？如果缺少信息，工作停在哪里？下面这张映射可以帮助团队把问题说具体。它描述当前材料中的关系，处理办法属于设计建议。

| 交接位置 | 接收方还缺什么 | 可以安排的下一步 |
| --- | --- | --- |
| T02 进展进入周报 | 符合验收口径的状态及证据 | 分开记录开发自报、现场结果和待核对问题 |
| 导出结果进入说明 | 经验证的操作结果 | 约定提供验证记录，说明按实际范围编写 |
| 改期建议进入计划 | 赵明的决定 | 保留原期限，单独呈现建议与待确认事项 |
| 问题清单进入反馈汇总 | 明确的汇总负责人 | 由有权分派的人确定承担者并留下记录 |

不必一次画完整个企业。挑一个经常被催问的交付，往前追问它依赖什么，往后追问谁会使用，就可能发现个人任务清单里没有显现的连接。

### 等待背后有几种不同的问题

有人说“我还在等”，首先应弄清他等的是什么。周宁等待导出验证，是工作依赖：缺少可靠结果，写下去就可能返工。改期等待确认，是决策依赖：建议已经提出，生效条件尚未满足。反馈汇总没有负责人，则是任务还未被承接，提醒所有人“抓紧处理”并不能自动补上这个位置。

这几种情况需要不同动作。工作依赖应明确上游要交出什么，以及条件尚未满足时下游可以先做哪些部分；决策依赖应把问题、原安排和可选影响交给相应负责人；无人承接则需要分派。把它们统称为“协同不够”，容易让团队增加群消息和会议，却没有减少等待。

等待也未必都要取消。一次重要审阅可能是值得保留的判断环节。需要分辨的是：时间用于比较方案和检查质量，还是用于找材料、猜口径、确认谁能决定。前者需要人投入，后者更有可能通过共同的信息和明确的交接得到改善。

### 先改一处连接，再看工作是否接上

如果这个模拟团队决定尝试，可以先选“导出验证结果交给说明编写者”这一处。设计延展是：由相关人员商定一份共同引用的任务记录，写明验收条件、当前证据、尚缺事项、下一步承担者，以及状态记录的时间。验证结论尚未出现时，记录如实保留等待；有新结果后，由有权确认的人更新，相关说明再引用这份记录。

这会增加一点维护工作，因此要让同一份记录服务多处使用。周报引用它，说明编写者也从这里确认可写范围，协调人不必为每个人重新口头解释。记录需要足够短，让维护者愿意更新，又要能回到原始依据。把每次聊天都复制进去，接收人仍要从头寻找答案。

还应留下少量观察时间点：上游何时提供可用材料，下游何时收到、何时能够开始，以及为什么退回。无需一开始就追求漂亮的统计，先判断等待究竟发生在哪里。若材料已经齐全而下游仍被其他工作占满，继续缩短上游整理时间，就不会改变这一段的排队。此时需要讨论工作安排，而不是再改一遍提示词。

### 个人成果怎样成为共同依据

第 3 章的来源对应表，为组织协作提供了一个起点。下一位使用者能够知道结论依据哪些记录，遇到变化时也知道回到哪里核对。但一个项目的来源表仍有边界：哪些规则在下一个项目继续有效，谁负责解释“验收通过”，离开这个群聊后又到哪里找到它们？

团队可以从一次交接里挑出值得共同保存的内容：明确的术语、反复使用的判断规则、可靠的来源入口，以及处理例外时需要联系的人。对于仍在变化的任务状态，则保留对应时间和更新位置，避免把一份周报永久当作最新事实。

组织改善从这里开始变得具体。个人交出的文件能被别人理解和采用，发生分歧时有依据可查，遇到新情况时有人维护。这些共同条件逐渐形成后，Agent 才更容易在不同成员之间接上工作。下一章要讨论的知识基座，就是把这些条件组织起来，让它们在需要时找得到、用得上。

## 第 6 章 共建企业的知识基座

### 从“资料在哪里”问到“这次能不能用”

设想模拟培训项目进入下一轮讨论，一位新加入的同事问：“名单导出已经可以用了吧？”有人发来开发进展，有人转来会议纪要，两份材料说法不同。即使所有文件都已经集中保存，新同事仍需要知道采用哪条口径、看到哪个时间点、向谁确认。

这正是企业知识基座要解决的问题。本书用这个名称指共同组织和维护的业务知识及其来源关系，让员工和 Agent 能找到适用信息、理解边界，并知道发生变化后该找谁。它可以从少量相互关联的记录开始。资料数量增长，并不自动意味着这些条件已经具备。

有时人们把进一步连接模型、系统工具和人的判断的整体称作“企业大脑”。这是帮助理解协同关系的比喻。组织仍需具体回答：保存什么，依据何在，谁能使用，谁来更新。名字可以不同，这些问题无法省略。

### 共同依赖的内容，有不同的性质

模拟项目中的“字段清单已确认”是有来源的事实；“两项功能都通过才算验收通过”是规则；“截至会议时导出失败”是特定时点的状态。把它们混在一个段落中，读者可能看得懂，复用时却容易误判。一条规则可以继续适用，一条状态可能下一次验证就会改变。

团队可以先用下面这张知识地图检查自己保存了什么。表中沿用模拟材料的内容有明确来源；责任维护与权限安排属于设计延展，需要团队实际约定。

| 内容 | 需要说明的问题 | 培训项目中的例子或设计 |
| --- | --- | --- |
| 事实 | 发生过什么，依据在哪里 | P01 记载项目目标与角色，M02 记载现场现象 |
| 经验 | 在什么条件下，这种做法值得再试 | 从本次材料提出“自报与验收分列”的复用建议，注明适用边界 |
| 规则 | 什么条件下应当怎样处理 | P02 规定验收条件和期限调整权限 |
| 状态 | 哪个对象在什么时间处于何种情况 | 截至 11 月 6 日 18:00，材料未见 T02 通过验收的依据 |
| 责任 | 谁能解释、确认和维护 | 项目既有决定权限按计划；知识维护者另行指定 |
| 权限 | 谁可读、可改、可据此执行 | 设计时分别设置项目查看、维护和业务操作范围 |

经验尤其容易被过早写成规则。一次材料整理提醒我们关注“开发自报与验收”的区别，足以提出一条可供验证的做法；它不能证明所有项目都必须使用同一套状态名称。经验条目应保留情境，规则条目则要有明确的制定依据。

### 让一条知识能够被追问

不妨围绕已知的验收规则设计一条知识记录。以下只是知识条目设计例子，没有替模拟团队增设已经生效的制度。条目的正文可以很短，支持追溯的信息要一同保存：

```text
条目标识：TRAIN-RULE-01
名称：报名表演示版的验收口径
内容：字段正常提交、名单正常导出，两项均通过才可报告验收通过。
性质与范围：规则；仅适用于本模拟项目的 T02。
依据：项目计划 P02；来源文件版本为 2026-11-02。
业务确认：原计划已载明本规则；后续变更按项目决定权限处理。
维护责任：建议由团队指定维护者，当前设计未指定具体人员。
关联：T02 状态记录、验证依据；状态另行更新。
版本与复核：保留本条修订记录；验收范围变更时复核。
访问边界：沿用来源材料的授权，实际配置前确认。
```

稳定标识让别的文件可以引用这条规则，而不是重复抄写。来源说明让使用者能够核对文字是否准确。适用范围防止它被带到别的培训流程后，误作全公司的通用制度。关联状态则提醒读者：知道完成条件，与知道现在是否完成，是两回事。

出现分歧时，这些信息也能帮助定位问题。如果 Agent 引错规则，应修正引用；如果来源规则本身需要改变，应交给有权决定的人。维护者可以整理条目、补齐链接，但这项编辑职责不自动赋予他改变业务规则的权力。

### 为当前任务组织相关知识

企业可能积累了许多培训规则，但写本周周报时，不需要把全部材料都交给 Agent。当前任务需要的是本项目目标、报告时间点、有效规则、相关状态、待确认事项和交付要求。共同知识提供可依赖的基础，任务上下文把其中相关的部分组织到当前工作里。

Anthropic 的上下文工程说明把指令、工具相关信息、外部资料等放在一起考虑，并强调为任务选择合适的信息。这为组织单次任务的输入提供了一个参考。[上下文工程参考](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

例如，整理截至 11 月 6 日的周报，应保留那个时点的材料快照；以后即使任务状态更新，也不能用新状态悄悄覆盖当时的报告。另一项新任务若要准备下一次演示，就应查询最新有效记录，并注明查询时间。共享来源可以相同，取用的版本、范围和目的可能不同。

同样，个人这次偏好的文字长度、尚未证实的排查猜测、临时讨论中的个人信息，不必都进入共享知识。先问它是否有后续用途、适用范围是否清楚、是否允许共享，可以避免知识基座被单次任务的细节淹没。

### 按角色使用，也要按角色承担责任

共同依据不意味着所有人看到所有内容。培训协调人可能需要查看报名处理状态，课程讲师只需要必要的授课信息。这里是在说明一种权限设计思路，模拟材料没有包含真实报名人员信息，也没有既定访问配置。

微软对 Copilot 的说明提供了一个产品例子：它按用户既有权限使用工作内容，并提醒用户核查来源；这不能替代对其他工具权限行为的核实。[企业数据与来源说明](https://support.microsoft.com/en-us/microsoft-365-copilot/what-information-does-copilot-use-to-answer-my-prompt)

知识记录的可见范围、Agent 可调用的业务操作、操作后的确认要求，需要分别决定。一个人能阅读验收规则，不等于他有权关闭任务。知识基座也不应为了便于搜索，悄悄扩大原文件的可见范围。权限发生变化时，目录、摘要和关联条目都需要检查，避免正文收回后，摘要仍在传播相同信息。

### 从一组能用的知识开始

开始共建时，可以选择上章找到的一处交接，把接收人反复询问的问题整理出来。培训项目可以先围绕验收口径、期限调整规则、项目状态入口和相关负责角色形成一小组记录。请实际使用者拿着它们回答一个具体问题，观察仍缺什么，而不是先规定每个部门上传多少份文档。

如果问题出在来源找不到，就补来源；如果两种说法适用不同范围，就分别标清；如果没有人能确认，以尚未核实内容保留，不能包装成已生效制度。这样的整理让知识的可靠程度可见，也让共建者知道下一步需要补什么。

条目建立之后，真正的考验才开始：谁会在规则变化时想到它，使用者如何指出问题，旧版本怎样退出当前使用。知识基座需要进入日常工作的更新循环，才能继续被共同依赖。下一章就从一次贡献如何进入、又如何离开这个循环谈起。

## 第 7 章 让知识在工作中持续生长

### 用过一次，才知道哪里还没有讲清楚

一条知识刚被整理出来时，往往看上去已经完整。直到有人拿它做事，才发现省略了前提：适用于哪个项目，所谓“完成”是谁确认的，遇到例外又应找谁。知识共建的后半段发生在使用中。上传文件只是提供材料，真正让知识继续生长的，是问题能否回到有能力处理它的人手里。

本章继续围绕模拟培训项目作设计延展。下面提出的贡献、审核和维护安排，都是可供团队采用的办法，尚不是这个模拟项目已经运行的组织制度。原始材料仍停留在第 3 章的报告时点；导出问题没有新增的修复结论，改期也没有新增批准。

明确这一点很有必要。知识维护容易产生一种错觉：条目写得越来越完整，事情仿佛也已经解决。实际上，共建既要补充知识，也要诚实保存暂时不知道的部分。

### 贡献从工作里的一个小发现开始

不必要求每个人工作结束后再写一篇完整经验。发现一个来源失效，指出一条规则遗漏适用范围，补充一个可核对的例子，都可能帮助下一位使用者。贡献入口应允许人用很短的文字说明：在哪里遇到问题，建议怎么改，依据是什么。

例如，周报整理者可以提出一个候选经验：“进展记录中的开发自报，应与按项目口径判断的验收状态分列。”贡献时带上 P02、R02 和 M02，说明这条建议来自同一项目中不同记录的冲突。还应写清局限：它是针对这类交接的做法建议，未证明在所有业务中都适用。

Agent 可以协助从交付物中提取候选内容，把来源、问题和建议整理成条目。候选记录应与正在使用的知识分开显示。若它根据导出失败写出“通过某项设置即可修复”，就超出了材料；这部分不能因为语言具体而进入经验库。原记录只支持观察到的现象和待排查状态。

一个轻便的贡献入口能减少额外负担，但“轻便”不等于没有依据。找不到来源的建议也可以提出，只需标为尚未核实，并说明需要谁补充。这样既保留线索，也避免使用者把猜测当作已经验证的知识。

### 审核要找到能回答这个问题的人

审核不宜变成所有内容都交给同一个管理员。知识维护者可以检查链接、字段、重复和版本，业务问题则需要熟悉相应领域、具备相应确认权限的人判断。如果修改涉及既有规则，确认方式还要遵循业务本来的决定权限。

围绕上述候选经验，审核者需要检查三件实际的事：来源是否支持描述，建议的适用范围是否足够清楚，现有条目是否已经表达了同一做法。如果只是给已有规则补充一个说明例子，可以关联进去；如果另立一条经验更有助于使用，也要指向原规则，避免今后两处各改各的。

审核的结果可以是纳入、退回补充、并入已有条目，或暂不采用。暂不采用也应留下简短理由，比如依据不足、范围过宽、已被另一条覆盖。贡献者由此知道怎样改，维护者以后也不必重复讨论同一问题。

这套安排需要承认业务骨干的时间有限。低风险的文字纠错可以按团队约定简化处理；会改变执行要求的内容则必须认真确认。把所有修改都按同样复杂的程序流转，会使小错误长期没人愿意修，把重要变化也挤进等待队列。

### 让使用和反馈连到同一条记录

条目投入使用后，引用位置越清楚，反馈越容易处理。周报或任务委托引用稳定标识与相应版本，使用者发现问题时，就能从工作成果回到具体条目，而不用说“知识库里有一份文档不对”。

反馈还应带上使用情境。例如，“按这个条目写说明时，无法判断导出结果应由谁确认”，比“这条知识不好用”更有帮助。维护者可以判断：条目确实少了交接安排，还是使用者需要的信息原本属于当前任务状态。前者应完善知识或安排讨论，后者应给出状态入口，避免把所有动态信息塞进规则正文。

遇到两份有效记录看似冲突，不能让 Agent 自动选一句顺耳的答案覆盖另一句。先看范围和时间是否相同；如果确属同一事项的冲突，保留分歧，联系相关确认者。在结论出来之前，可以提示使用者此条不宜直接作为行动依据，并提供可联系的位置。

反馈是否被接住，比入口是否醒目更重要。团队需要约定谁查看新反馈，超出其判断能力时交给谁，处理结果怎样回告。否则，只是给使用者增加了一项没有后续的填表工作。

### 更新也包括让旧知识退出

知识有不同的变化节奏。规则需要在制度或业务范围改变时复核，操作经验可能在流程调整后失效，项目状态则随着工作推进更新。不能给它们统一贴上一个“长期有效”，也不必机械地要求所有条目每周重审。

设计维护办法时，可以为条目写明触发复核的事件。培训验收范围变化，应提醒检查关联规则；任务结束，应检查哪些临时状态还在默认检索结果中；负责人离岗或换岗，应检查维护责任是否已经转交。对较长时间没有触发事件的条目，再安排定期抽看，防止变动没有被记录。

退出当前使用不必等于删除。旧规则和历史状态可能仍是解释过去报告的依据，可以保留为历史版本，写明停止适用的时间、原因和替代条目，并从默认使用入口移开。没有替代内容时也应直说，不能让旧知识因为搜索方便而继续承担当前依据。

对于来源失效、暂时无法核实的内容，可以先限制其作为行动依据的用途，等确认后恢复或退役。这个处理会让眼前可用的条目变少，却能保护使用者对知识基座的信任。

### 把维护放进日常工作，也给维护者位置

要让上面的循环运转，可以从一个小团队开始约定：交付时顺手提交值得复用的候选内容；由轮值维护者集中整理问题，领域负责人处理需要业务判断的事项；在既有工作回顾中留一段时间，查看反复被问、被退回或找不到依据的内容。具体频率由反馈量决定，不必为了知识共建再增加一串例会。

管理者需要给维护留下明确的工作时间。业务骨干承担了核实和解释，却仍被要求保持原有交付量，知识工作就只能挤到空闲时完成。可以把维护责任纳入工作安排，在任务分配时讨论负担，也允许贡献者说明自己无力长期负责。

评价贡献时，应看它帮助了什么判断、解决了什么歧义，而不是只数上传篇数。指出过期条目、合并重复内容、明确拒绝一条无依据的建议，都值得被看见。使用者可以在反馈中说明哪处帮助了自己，团队也可以在回顾时展示一条知识从问题到修订的过程，让维护的价值有具体落点。

当这些安排进入日常，知识共建就有了持续的来源：工作产生候选内容，审核使依据和范围清楚，使用暴露缺口，维护让变化继续被接住。接下来，还需要让适用知识能够支持实际行动。下一章将把视线转向模型、系统与工具，看看一项任务怎样从知道该做什么，走到能够执行并留下结果。

## 第 8 章 接上模型、系统与工具的能力

### 从知道一件事到完成一件事

前几章讨论了团队可以共同依赖什么知识，以及知识怎样更新。现在把问题往前推一步：Agent 已经知道验收规则，也找到了最新记录，接下来能做什么？

以培训报名项目为例，周报可以指出改期尚未获得批准，但这句话本身不会产生一条改期申请，更不会改变项目系统中的日期。写出建议、提交申请、获得批准、更新任务，是几种不同的业务动作。组织要让 Agent 参与执行，就要把这些动作分别接到能够承接它们的人和系统上。

本章继续采用假设设计，说明这个模拟团队如果接入业务工具，可以怎样安排。原材料中的改期仍未见批准，演示版仍缺少通过验收的依据。下面谈的是下一步怎样建设，没有新增实际运行结果。

一条完整关系可以画成：

```text
任务目标 → 取得相关知识与当前状态
模型形成步骤 → 工具查询或执行
业务记录与操作回执 → 验收判断
符合约定：完成交付
需要接续：保留已有记录，转交相应处理者
```

这张图中的每一处连接，都有具体的业务问题需要回答。

### 为这次任务取出相关内容

假设协调人交给 Agent 的任务是“整理待确认事项，准备改期申请”。它需要原计划中的验收口径和日期、会议中的建议、项目负责人的身份，以及系统中是否已有申请。完整的培训制度、往年课程讲义和所有员工名单，对这一步未必有用。

相关内容也有新旧之分。会议记录能证明会上提出过什么，却不能单独证明会后是否已经有人作出决定。提交之前，应查询当前的申请状态；没有查询能力时，就把状态未知作为限制交给协调人，不能靠旧材料猜测。

任务上下文由此逐步形成：先从共同知识中取得规则，再从业务记录中取得状态，发现缺少信息时补查。模型据此理解目标、拟定步骤和整理表达；算力支持这些处理运行，实际查询和修改仍需要工具承接。增加算力并不会自动补上缺失的审批记录。

团队可以先问一个朴素的问题：如果换成一位刚接手的同事，他需要知道什么才能开始，遇到什么情况必须停下来询问？这些内容，往往比一次放进更多资料更有帮助。

### 工具说明和实际能力要同时具备

“查询项目状态”这句话太宽。工具说明应让 Agent 知道，它查询哪个项目、返回哪个时点的记录、能否看见待审批事项，以及空结果意味着什么。“没有找到申请”与“当前账户无权查看申请”，会带来完全不同的下一步。

能力的用途、输入要求、返回内容和使用条件，属于 Agent 理解与选择工具时需要的上下文。真实查询还要有可连接的系统、允许使用的账户和正常运行的环境。把一份操作指南放进知识库，并不等于已经接通了指南中的系统。

Anthropic 关于工具设计的说明强调清楚界定工具用途、输入输出，并用实际任务评价工具是否有效。这为接入工作提供了设计参考，不能代替本团队的检验。[工具设计参考](https://www.anthropic.com/research/writing-tools-for-agents)

业务人员不必先掌握接口细节，可以与系统维护者共同核对一项能力：给出什么信息，允许完成什么动作，回来时能凭什么判断结果。说明写得清楚但能力不可用，任务会停在执行前；能力已经接通而说明含糊，也可能把正确动作施加到错误对象上。

### 让查询和提交各有边界

在这个设计例子中，Agent 可以先核对原日期、改期理由和验收条件，形成申请草稿。协调人确认内容后，它才在获授权的范围内提交。提交成功只表示申请已经进入流程，项目日期仍应等有权批准的人作出决定后，再按规则更新。

这几个步骤适合分别记录。草稿记载准备了什么，申请记录记载实际提交了什么，审批记录记载谁作出了什么决定。周报引用哪一种记录，也就决定了它能够写到哪一步。

查询与修改还可能面向不同范围。协调人也许能查看项目整体状态，却只能编辑自己负责的事项。工具应执行这种范围，任务委托也应据此限定目标。不能因为 Agent 读到了一个字段，就默认它能够或应该修改这个字段。

连接初期，可以先让 Agent 查询和准备材料，把正式提交留给人。等业务规则、回执和异常处理经过检验，再决定是否扩大执行范围。选择范围的依据，是出错后会影响谁，以及团队能否及时发现和处理。

### 失败之后，先弄清业务停在哪里

设想申请提交后，页面一直没有显示结果。此时最危险的处理，是把“没有看到成功”当成“没有提交”，立即再做一次。前一次可能已经进入审批，只是回执没有传回来。重复提交会让负责人面对两份申请，也可能产生相互冲突的更新。

团队需要为同一项申请保留可识别的任务记录。恢复执行时，先凭记录查询是否已经受理，再决定重试、补交还是转人工。如果系统能够防止同一任务重复提交，应明确启用并检验；如果做不到，就应限制自动重试，把不确定状态交给能够核对的人。

其他失败也要分别处理。没有权限，需要有权人员接续；材料缺失，需要补充事实；业务规则拒绝提交，需要解释原因；系统暂时不可用，才可能适合稍后重试。让 Agent 反复尝试，不能解决这些性质不同的问题。

异常交接应留下已完成的步骤、最后一次操作、收到的回执和仍然未知的状态。接手的人据此继续，才能避免从头询问，或把已经执行的动作又做一遍。恢复能力在业务上的意义，是让一次中断不再变成新的混乱。

### 把回执接回工作记录

工具返回“成功”，仍需理解它成功完成了什么。保存申请草稿、送出申请、审批通过、更新日期，不能共用一个含糊的完成状态。回执最好能够对应具体对象、动作、时间和当前状态，让人回到系统核实。

假设未来一次申请实际完成提交，Agent 应更新的是“已提交、待审批”，并附上可查的申请记录。只有取得批准依据并完成后续更新，才可能把相应任务写成已办结。这个条件说明没有改变本书原案例中尚未批准的事实。

验收时可以从最终业务记录反向查看：对象是否正确，变更是否符合授权，原有信息有没有丢失，相关人员能否继续工作。对影响较大的动作，还应检查系统中的实际状态，而不能只读 Agent 最后写出的报告。

运行记录也不宜全部变成企业知识。某次申请结果属于项目事实；反复出现的状态歧义，经过核实后，才可能成为需要修订的工具说明或协作规则。知识与执行因此相互反馈。下一步要考虑的，是这些动作接入之后，原来的分工和交接是否仍然合适。

## 第 9 章 重新定义工作、流程与分工

### 工作的边界会随着能力改变

一份文件可以代表工作成果，也可能只是工作途中的一个位置。周报把问题整理清楚之后，如果没有人承接待确认事项，组织仍然需要另外安排一次协调。接上 Agent 和业务工具以后，值得重新讨论的，正是这些位置怎样连接。

本章沿用模拟培训项目作流程设计延展。原材料中的改期和验收状态保持不变，下面的安排是供团队讨论的方案，不是已经实施的制度。我们尝试从“谁负责哪份文档”，向前追问“谁负责让哪项任务进入下一步”。

这个变化不要求每个人承担更多没有边界的事情。相反，它需要把目标、输入、交付、接手条件和异常去向说清楚。任务变得完整，责任也应变得可以承担。

### 从交出材料到接续结果

假设团队将“整理本周进展”定义为一项任务。原来的结束点可能是周报发到群里；新的结束点可以包括：按共同口径形成状态，列出需要决定的问题，确认由谁接手，并保留接手记录。是否包含后面的业务处理，需要另行约定。

这样的定义让协调工作具体起来。林岚可以负责组织问题和跟踪接续，陈屿负责说明排查与验证，周宁依据可靠结果编写说明，赵明承担计划规定的期限决定。Agent 帮助整理、提醒、核对与准备记录，不能因为参与了多个环节，就接管所有人的业务判断。

各角色之间也需要明确什么叫“接到了”。一条消息发出，未必有人已受理；有人受理，也未必已经作出决定。状态名称不需要很多，却应分别支持这些不同的后续动作。任务的结束条件因此可以被下一位使用者理解。

### 用一张对照检查改造是否完整

可以先把原流程与提议的安排放在一起。以下对照是模拟项目的设计例子，具体分工和授权应由团队实际确认。

| 位置 | 容易出现的原有安排 | 可讨论的改造安排 |
| --- | --- | --- |
| 任务提出 | 各自口头理解“整理进展” | 明确成果使用人、统计时点、状态口径和接手条件 |
| 材料处理 | 每个人查找并复制自己的版本 | 按角色取用共同来源，Agent 保留引用和缺失 |
| 需要决定 | 问题混在整份报告里等待被看见 | 提炼具体问题，由相应负责人受理并记录决定 |
| 执行与更新 | 决定留在聊天中，相关记录各自修改 | 在获授权范围内更新业务记录，核对受影响的交付 |
| 异常 | 出现问题后重新找人解释 | 连同已做步骤和未知状态交给约定角色处理 |
| 任务关闭 | 文件已经发出 | 对照约定确认成果可用、接续已完成，保留未关闭事项 |

对照之后，可以请每个参与者用自己的话解释：我从哪里开始，交出什么，什么情况需要别人作决定。若解释不同，流程图还没有真正成为共同方法。

### 让人的判断落在值得判断的位置

引入 Agent 之后，审阅不宜只是增加一位“看过”的人。需要明确这次审阅要判断什么：事实是否充分、方案代价是否可接受、是否改变既有承诺，或成果是否适合下一步使用。不同问题可以由不同角色处理。

例如，字段提交与名单导出的检查可以按已约定的标准执行，出现不一致时交给相关人员核实；是否调整期限，则需要计划规定的负责人决定。每一次查询都等待批准，会制造新的排队；没有判断依据就把重要决定交出去，又会使责任失去落点。

团队可以从动作性质和影响范围讨论自主程度：允许在指定材料中查询，允许准备草稿，允许在明确条件下更新某类记录。每种安排都需要对应的观察和恢复办法。是否扩大范围，取决于实际任务中的证据，而不是对某个岗位统一规定“全部自动”或“全部人工”。

### 异常处理也是正式工作

流程设计常把正常情况画得很顺，真正消耗时间的却是材料缺失、口径冲突、系统没有回应，或事情已经超出原先范围。异常如果没有接续位置，就会重新落到最热心的人身上。

可以把异常工作分成发现、判断和恢复。Agent 提出具体差异，附上相关依据与已执行动作；具备业务职责的人判断下一步；恢复之后，把当前状态和必要经验写回记录。这并不要求每种例外都预先写完，而是要让未知情况有一个能够接住它的入口。

中间协调工作也会因此改变。重复搬运状态可能减少，解释冲突、处理依赖和协商优先级仍需要人承担。组织是否减少某种层级，不能仅从工具能做多少步骤推出；应看原来由这些角色承担的判断与协调，究竟转交给了谁。

### 让承担工作的人参与设计

最接近工作现场的人，往往知道哪些例外在文档中没有写出。改造前可以让他们走一遍真实任务：哪些地方总要询问，哪条规则事实上存在多种解释，什么信息即使能取得也不足以继续。

讨论也应包括新增负担。谁维护知识，谁检查 Agent 的交付，异常出现时谁暂停手头工作来处理？这些职责占用时间，需要进入任务分配。可以减少重复填报，把现有记录作为依据，而不是让大家在原工作之外再维护一套平行说明。

工作方式改变还需要训练。让员工有机会解释判断、比较 Agent 的方案，并参与修订共同方法，有助于形成实际采用的条件。只宣布新流程，却不给材料、工具和练习空间，不能算已经完成组织调整。

### 把流程提议带到实际任务中

一份新的分工对照只是设计起点。选择一段交接、一次明确的任务，检验接收人是否拿到了可用结果，异常是否找到了处理者，原来的等待是否减少，又增加了什么维护工作。

有些安排需要保留，有些可能需要简化。若记录字段太多、审阅集中在少数人手里，或员工仍在私下建立第二套状态，都是值得回到设计上讨论的信号。把这些信号带入试点，比一次宣布全面改变更容易形成可修正的经验。

下一章将进一步讨论怎样观察这些变化，给组织改善留下足够的依据，再决定是否扩大使用范围。

## 第 10 章 把试点变成组织改善

### 先确定试点要改变哪一段工作

团队已经有了共享知识、可用工具和流程提议，接下来需要回答一个具体问题：这些安排是否帮助工作更好地完成？试点应从这个问题出发，而不是先规定所有人每周使用多少次 Agent。

以培训项目作设计延展，可以选择“导出结果进入操作说明”这一处交接。上游交出可核对的验证记录，下游据此编写，遇到缺失时明确退回或保留等待。试点观察的是这段工作能否接上，没有预设它一定更快。

开始前写清边界：包含哪些角色和材料，采用哪些工具，哪些判断仍由谁作出，怎样认定一项交付可用。范围足够小，参与者才容易解释发生了什么；范围也要足够完整，才能看见整理、交接、检查和返工的总投入。

### 留下原有情况，才能理解变化

如果没有原来的记录，试点结束时常会只剩下“感觉方便了”。这样的感受有价值，还需要与具体工作对应。可以回看相近任务的开始、接手、退回和完成时间，以及出现过的主要问题，再选择其中能够持续取得的观察点。

任务不完全相同，应保留影响比较的条件。材料数量和完整程度、复杂性、参与者经验、同时承担的其他工作，都可能改变结果。需要时把任务分组讨论，避免把一个简单任务与过去最困难的一次作比较。

如果团队具备条件，可以比较同期仍采用原做法的相近任务；条件有限时，也可以逐次记录改变及结果，承认能够解释的范围。无论采用哪种办法，都应说明还有哪些条件同时变化，避免把全部改善都归因于 Agent。

### 看完整流程，也听实际使用者

评价可以从几项共同关心的结果开始。下面是供试点改写的记录框架，表中没有填入模拟的成效数字。

| 观察对象 | 可以怎样记录 | 用来回答什么 |
| --- | --- | --- |
| 交付质量 | 事实、遗漏、完成口径和使用者退回原因 | 成果是否更接近实际需要 |
| 整体周期 | 从任务受理到接收方可采用，区分处理与等待 | 个人加快后，工作是否真的向前移动 |
| 总投入 | 准备、干预、核查、返工、工具费用和维护 | 改善是否把成本转移到别处 |
| 知识与工具 | 缺失、过期、访问失败、重复执行和恢复记录 | 哪些基础条件影响结果 |
| 员工体验 | 反复询问、临时打断、职责清晰度与学习机会 | 使用者实际承受和得到什么 |

不必每项都建立复杂系统。已有任务时间、退回意见和简短回顾，可以先形成观察基础。更重要的是口径前后一致，参与者知道记录用于什么，并能指出遗漏的负担。

数据也需要与具体过程互相解释。周期缩短可能来自等待减少，也可能是本次参与者没有其他紧急任务；人工检查增加，可能暴露了过去没有认真检查的错误。把过程带回来，才能判断应保留什么，而不是只挑一个有利的数字。

### 从研究中形成适合自己的问题

一项公开研究提供了具体的观察入口。[Brynjolfsson、Li 与 Raymond 的《Generative AI at Work》作者版本](https://arxiv.org/abs/2304.11771v2)研究客服场景中分阶段引入生成式 AI 助手，发现效果在工作者之间存在差异。它提示我们注意场景、经验与任务条件，不能把该研究直接当成所有 Agent 或组织整体都会得到同样效果的保证。

团队据此可以提出自己的问题：新人和熟悉业务的人是否遇到不同困难？知识质量改善后，谁更容易采用？最复杂的例外是否仍然全部集中到少数人？问题应回到本团队的任务，不必套用其他场景的平均结果。

也应保留未采用和未完成的任务。只挑顺利案例展示，会遗漏工具不可用、资料不足和员工选择原做法的原因。了解这些原因，能够帮助团队收窄适用范围，或补上真正缺少的条件。

### 让复盘形成一个明确的决定

试点结束后，可以把观察结果、使用者意见和仍不确定的部分放在一起，讨论下一步。继续使用需要说明哪些任务已经有足够依据；调整需要明确知识、工具或流程中的哪一处改变；缩小范围则应指出当前方法适合和不适合什么。

暂停也可以是合理结果。例如，现有工具不能取得关键状态，导致大量人工核对，先补齐业务记录可能更有效。暂停时保留已经形成的材料和判断，说明恢复前需要满足什么条件，避免下一轮从同一个问题重新开始。

这些决定要落实到责任和资源。若继续，需要谁维护知识、处理异常、支持工具；若调整，谁负责验证新安排。没有这些接续，试点可能留下漂亮报告，却没有留下可持续工作的方法。

### 推广需要重新检验适用条件

一种方法在熟悉业务的团队里有效，换到人员、资料和系统不同的部门时，仍需适配。推广包可以保留目标、输入条件、业务口径、工具依赖、职责、常见例外和评价方式，让接手的人知道怎样判断是否适合。

不必把全部细节写成不可更改的步骤。共同规则应清楚，本地可以调整的内容也应清楚。新团队用过之后，反馈哪些部分直接可用、哪些需要补充，再由共建者修订。推广因此也是继续学习的过程。

对组织而言，试点最有价值的成果包括一套可采用的方法，也包括它的边界：何时适用、怎样维护、遇到什么信号需要重新判断。下一篇进入集团和更大协作范围时，我们将带着这些条件继续检验，共同能力怎样跨越不同现场。

## 第三篇 从企业集团走向行业与时代

方法来到不同部门、业务单位和合作伙伴之间，需要重新检验适用条件。本篇沿着集团、经营生产、供应链和劳动变化逐层展开，讨论更大范围的积极影响怎样发生，以及参与者能够如何推动。

## 第 11 章 集团协同，让共同能力跨越部门与地域

### 当一种做法来到另一家单位

一个团队把培训报名任务理顺之后，总部可能希望把方法交给其他业务单位。共用报名规则、自动核对材料、汇总进展，看起来都值得复用。但接手的人很快会问：我们有轮班员工，也能按同样的时间报名吗？总部课程与本地课程怎样区分？名单应该由谁查看？

下面是对前文模拟培训项目的设计延展，设想一家集团的总部与三家业务单位共建培训能力，并非已经开展的集团实践。三家单位分别以办公室、门店和生产班组为主要工作场景。它们需要共同了解培训安排，却不能把人员范围、时间和执行办法全部照搬。

集团协同由此遇到一个具体问题：怎样减少重复建设，同时让方法适合当地工作？如果总部只分发一套模板，本地仍要自己补齐条件；如果要求所有单位完全一致，员工又可能在系统之外另做记录。共同能力要在这两种摩擦之间找到可采用的安排。

### 把共同知识分成可以维护的层次

先找出真正需要共同解释的事。例如，一门课程怎样识别，报名人数与实际参与人数分别指什么，取消、候补和完成怎样记录。这些口径影响跨单位汇总，应由集团范围的业务负责人组织确认。各单位使用同一个名称时，才有相同的比较基础。

具体到排班安排、现场联系人和本地课程，可以由业务单位维护。某次培训临时更换场地，则属于当次任务的状态，不必升级为集团规则。知识分层的目的，是让改变发生在恰当的位置。一个门店调整课程时间，不该等整个集团更新；集团改变统计口径，也应让各单位知道从哪个周期开始采用。

| 层次 | 共建内容 | 维护与使用安排 |
| --- | --- | --- |
| 集团共同层 | 课程标识、状态含义、统计口径、共用任务方法 | 总部业务负责人组织确认，单位代表参与修订 |
| 业务单位层 | 本地排班、课程补充、交接和服务安排 | 本地负责人维护，注明与共同规则的关系 |
| 具体任务层 | 本次名单、进展、临时变更与待确认事项 | 任务责任人更新，按参与角色提供信息 |

这份草图不要求把所有材料集中到同一个地方。共同来源可以由不同单位保存，只要标识、版本、访问方式和负责关系明确。总部统计需要人数及其口径，未必需要逐一读取员工的报名记录。

### 一份可复用的方法要带着适用条件

总部可以提供“核对培训名单”的任务方法，但它至少应说明输入材料、状态口径、交付物和人工判断点。门店单位还需要加入班次信息，生产班组需要核对工作安排，办公室单位则可能按部门归属汇总。共同方法提供骨架，本地补充决定它怎样落地。

复用也涉及执行条件。方法中写着“读取报名状态”，不代表每家单位都有相应接口。总部需要说明依赖哪个系统、需要何种权限、由谁支持接入；本地应验证自己的系统能否提供同样的信息。暂时只能提交文件的单位，可以先采用文件核对，清楚保留状态更新的时差。

因此，不能仅用“已经发布”判断推广完成。应看另一家单位能否独立说明何时适用，能否取得必要材料，能否接住异常和维护更新。一次成功复用，应留下本地增加了什么、哪些共同部分没有适用，以及原因。这些差异能够帮助总部修订下一版。

### 让贡献与维护都有工作位置

集团共建需要总部与本地共同投入时间。总部业务负责人负责共同口径与集团任务的取舍，知识维护人员整理版本和变更记录，系统支持人员保证共用能力有稳定的运行条件。本地业务负责人确认适用性，使用者反馈实际工作中缺少的信息。

这些工作不能全压在一位热心员工的业余时间里。总部若希望三家单位贡献方法，就应安排可用于整理、核对和培训的工时，并提供接入与维护支持。本地负责人也需要把参与共建计入工作安排，避免一边要求员工贡献，一边只按日常业务量考核。

资源分配可以从一项共同任务开始：先由总部承担共用口径和基础能力的维护，各单位承担本地材料核实与试用反馈。若某单位提供的方法被多处采用，应记录贡献，并让它参与后续调整。具体经费与工时怎样分担，需要结合使用范围商定，不能默认贡献最多的单位永久承担支持工作。

### 把共建放进一次跨单位任务

可以选择下一期集团培训作为设计中的试用任务。开始前，总部与单位代表对照一份历史报名材料，检查三个“完成”是否含义相同，确认共同口径，再分别补入本地条件。历史材料只用于准备；新任务的状态仍需从当期记录取得。

运行时，各单位先形成自己的核对结果，保留缺失与冲突；集团汇总引用已确认的状态，显示统计时点，并将无法比较的部分单列。总部能够看到共同任务的进展，本地人员也能沿着汇总回到自己负责的记录。任何一方提出规则修改，都应说明受影响的任务和开始采用的时间。

任务结束后，复盘不只问汇总用了多久，还要问本地补材料用了多久、共同口径解决了哪些争议、有哪些操作仍依赖总部解释。由此决定下一轮是增加支持、修改共用方法，还是保留本地安排。这是共建的反馈过程，不是三家单位都使用之后就算完成。

### 让推广接受不同现场的检验

总部看见统一报表，容易以为共同能力已经形成。本地的额外录入、等待和返工却可能藏在报表外。评价时应同时看集团任务的交付周期、各单位的实际投入、知识维护成本，以及结果能否支持下一步行动。

有的差异值得消除，例如同一状态有三种解释；有的差异应保留，例如不同班次需要不同安排。推广的工作，是逐次辨认两者，并让共用部分越来越可靠。集团获得的价值，来自单位之间能够理解、采用并共同改进一套做法。

当这套机制开始服务培训以外的任务，问题也会向企业的核心活动延伸。经营分析、生产安排和战略讨论，各自需要什么事实与判断？下一章沿着一项设备交付任务，继续考察共同能力怎样进入这些工作。

## 第 12 章 影响经营、生产与战略

### 从一张“交付吃紧”的报表开始

经营会上有人提出：“下个月交付会很紧，需要尽快扩充能力。”这句话可能来自已确认订单，也可能把销售预测一起算了进去。它还可能掩盖另一种情况：车间总体有空余，真正拥堵的是一套测试设备，或一种关键部件尚未到货。

本章采用一个说明情境：一家设备企业需要安排下一周期的交付，销售、采购、生产和质量部门分别保存着订单、到货、排程与检验信息。情境用于分析作用路径，没有对应的真实企业，也没有已经测得的经营成效。

Agent 可以参与整理这些资料，找到状态之间的联系，比较安排的后果。但企业能否按时交付，还取决于材料、设备、人员与实际执行。要理解办公中的变化怎样进入经营，需要把一份分析沿着行动向后追踪。

### 让事实进入能够作决定的位置

第一步是把“交付压力”拆开。哪些订单已经确认，哪些只是机会？交付日期来自客户要求还是双方确认？在制设备处在哪个环节，记录更新到何时？不同材料中的数量，能否对应到同一批设备？这些问题不解决，整齐的分析也可能把不同性质的信息加到一起。

Agent 可以按订单关联物料和检验状态，整理缺口，并把来源、统计时点和不确定项放在判断旁边。销售负责人确认订单范围，采购负责人核实供应状态，生产与质量人员确认现场条件。有人负责的事实，才有机会进入可执行的安排。

这一情境的作用路径可以写成：

> 可追溯的业务事实 → 发现限制交付的环节 → 形成可比较方案 → 负责人决定并安排执行 → 记录实际结果 → 修正下一次判断。

每个箭头都有条件。知道某部件短缺，只有接到可行的采购或调整措施上，才可能改变交付；形成计划后，还需要把决定写回订单和排程记录。分析文件留在会议附件里，路径就在这里中断。

### 在计划、采购和质量之间接住变化

设想某类部件的到货日期推迟，采购记录已经更新，生产排程仍按原日期安排。Agent 若能在授权范围内读取相关信息，可以列出受影响的订单、后续工序和需要确认的安排，让采购与生产讨论从同一批对象开始。

但“部件到货”与“可以投入生产”仍有距离。待检材料不能直接算作可用库存，替代件也可能需要质量人员确认适用性。对这些状态，Agent 应依据约定的含义整理影响，列出尚缺的判断，不能用一个看起来接近的状态填平差异。

一种可采用的分工是：采购提供到货依据，质量人员更新检验与替代判断，生产人员确认工序和设备约束，订单负责人协调交付承诺。Agent 持续整理变化及其关联，并在具备工具与授权时更新已经确认的安排。具体操作进入业务系统后，后续人员才能据此工作。

这里的改善可能来自更早看见一次冲突，也可能来自少做几轮跨部门解释。是否减少停等、返工或交付波动，需要在实际任务中观察，不能从资料整理速度直接推出。

### 把方案的代价摆到同一张桌上

面对到货推迟，团队可以比较不同安排：先生产材料齐备的订单；保持原顺序并协调供货；在质量允许的条件下采用替代件。Agent 可以按相同口径说明各方案影响的订单、必要条件、额外投入和仍未解决的问题。

比较时，不能只挑一个最好看的指标。调整顺序可能提高设备利用，却推迟已经承诺的订单；加急运输可能缩短等待，也会增加投入；替代件能否使用，应先由具备职责的人作出判断。模型能够组织信息，业务负责人仍要决定企业愿意承担什么代价。

可以请 Agent 对每个方案提出一个追问：“这一方案成立，最需要哪个尚未确认的条件？”如果答案是供应商能够提前供货，就应先核实，避免把愿望写成安排。决定作出后，保留采用方案、关键依据和需要重新讨论的触发条件，便于后续人员理解。

### 让战略讨论容纳不同的未来

连续几个周期出现交付压力之后，企业可能讨论增加产能、培养新的供应来源，或调整产品组合。这时，单次排程的经验只是线索。需求是否持续、瓶颈是否稳定、已有资源能否重新安排，都需要另外分析。

Agent 可以帮助整理两类情景：一类是假定需求持续、关键工序长期受限，比较增加能力与改进工序的条件；另一类是假定需求波动较大，比较弹性安排、供应合作和产品简化的作用。每种情景都列出假设，说明哪些观察会使它更可信，哪些变化会使原方案不再适用。

情景比较拓宽了讨论范围，不能代替对未来的判断。管理者需要结合客户关系、技术方向、员工能力和资源约束作出选择，并说明为什么优先采取某一步。可以先做能够检验关键假设的小规模行动，让后续投入获得更好的依据。

战略中的 Agent 因而更像一位能够反复整理材料、追问条件的参与者。它让不同意见较容易被摆出来，但不因为能生成一份完整方案，就拥有判断企业方向的责任。

### 让业务结果反过来修正知识

假如交付有所改善，仍需辨认原因。是信息更早到达，排程更合适，还是订单量下降、供应恢复？评价时可以比较相近任务的等待、返工、额外投入和交付结果，保留影响比较的其他变化。一次结果不足以确定长期效果，却可以指出下一轮值得检验的环节。

复盘还应回到原来的假设：哪一条到货信息不可靠，哪个检验状态经常被误解，哪种替代安排有适用边界。核实之后，将这些经验写回知识与任务方法；涉及承诺和资源取舍的决定，仍保存相应负责人的判断依据。

当共同知识、系统记录和人工决定能够这样连接起来，办公改善才有了影响核心活动的具体通道。这条通道并不止于企业内部。关键部件握在供应商手里，交付还依赖运输和客户接收，下一章继续讨论企业边界之外的协作。

## 第 13 章 沿供应链与行业扩展协作

### 双方说的是同一个日期吗

采购人员问：“备件什么时候到？”供应商的 Agent 很快回复“周五交付”，采购方的 Agent 也把周五写进计划。如果一方指发出仓库，另一方指到达现场，即使双方都使用了 Agent，原来的误会仍然完整地进入下一轮工作。

本章采用一个独立的说明情境：设备使用方、备件供应商和运输服务方准备改进一次备件交付协作。它与上一章的设备交付问题相连，但关注企业之间的接口。以下是试点设计与条件分析，没有对应的真实运行结果。

跨企业协作的起点，是发现彼此已经交换信息，却没有共同理解。在各自内部更快地产生消息，可能使往来更加频繁；只有信息能够被另一方准确接住，才可能减少共同任务中的等待与返工。

### 先共同解释一小组对象和状态

三方首先需要认出同一笔交付。采购订单、供应商发货单和运输单可能有不同编号，应有明确的对应关系。备件还需要规格与版本，以免名称相近而实际不能替代。共同标识让状态能够关联，不能替代对物品适用性的核实。

接着约定关键状态：“备货完成”由谁确认，“已发运”需要什么记录，“到达现场”与“接收完成”有何区别。交付日期至少说明事件、地点和当前性质，是预计、已承诺，还是已发生。发生变化时，相关方应知道旧日期为什么失效。

不必为此共享每家企业的全部经营资料。使用方需要知道与本次交付有关的可用数量、时间和限制，未必需要供应商完整库存；运输方需要接收要求和联络方式，未必需要订单的全部价格信息。共享范围由共同任务决定，各方保留对自身资料的管理责任。

### 让接口传递有依据的变化

一种简单的状态接口，可以围绕每次变化传递六件事：交付对象、发生了什么、何时更新、来自哪一方、依据在哪里、下一步由谁处理。它可以先表现为约定格式的文件或消息，不必一开始就建设复杂连接。

来源也要与事件匹配。供应商出库记录能说明货物已经出库，运输接收记录能说明承运方接到货物，现场签收记录支持接收状态。Agent 可以把这些信息关联起来，指出中间仍缺哪段记录。对方一条没有依据的“已完成”，不应自动覆盖本企业尚未确认的状态。

接口还需要处理变更。供应商改为分批发货时，应说明原安排与新安排的关系；使用方改变接收地点时，应确认运输方已收到并接受。各方约定怎样表示收到、接受、提出异议，以及超过约定时间后联系谁，才能减少“消息已经发出，工作却无人接手”的空档。

每家的 Agent 可以读取授权信息、检查差异并准备处理建议。涉及重新承诺交期、替换规格或确认接收的动作，应按照合作中商定的职责执行。工具连接得越顺畅，越需要知道哪一方有权更新哪一种事实。

### 共同收益需要有人愿意承担准备

统一编号、补齐记录和维护接口都需要投入。大企业可能减少了催问，小供应商却多了一套填报工作。如果这种负担没有被看见，“行业协同”就可能变成强势一方对另一方的新要求。

试点开始前，应分别记录三方的准备、日常处理和异常投入，再讨论分担。提出要求的一方可以提供格式说明、转换支持和联调时间；重复采用的数据尽量只提交一次；供应商能够用已有记录满足的，不应再要求手工抄写一份相同内容。

合作激励也可以很具体：使用方更早提供需求变化，供应商更及时反馈供货条件，运输方获得稳定的接收信息。各方都得到有用的信息，才有动力保持更新。若收益暂时集中在一方，就需要明确支持办法，不能只要求其他参与者相信未来会有好处。

### 做一次三方共同负责的试点

可以先选一种规格稳定、合作关系清楚的备件，在一条固定路线开展有限批次的试用。三方共同选出过去经常反复确认的问题，例如发运与到达的日期混用，把减少这类摩擦作为首要目标。试点范围和评价周期在开始前商定。

| 设计内容 | 本情境中的安排 |
| --- | --- |
| 共同对象 | 一笔交付及其订单、物品和运输记录对应关系 |
| 共享范围 | 相关数量、关键状态、预计与承诺日期、变更依据 |
| 负责关系 | 各方维护自身产生的事实，指定业务联系人处理争议 |
| 观察结果 | 重复确认、状态冲突、等待、实际交付及各方投入 |
| 调整依据 | 接收方是否实际采用信息，负担是否转移，异常能否解决 |

试用中保留异常过程：哪里使用了错误编号，哪条变化没有被接收，谁补充资料后恢复协作。这些记录帮助三方修正共同定义。不能只收集顺利完成的批次，也不能只计算其中一家少发了多少消息。

评价时还要区别信息改善与交付改善。状态更清楚，使等待原因更容易被看见，但运输能力不足仍可能延误。共同复盘应指出哪些摩擦已经减少，哪些需要业务资源或合作安排改变，再决定是否扩大范围。

### 从一段关系走向更大的协作范围

当一种接口在几个合作关系中可以复用，行业范围的共同定义才有了具体基础。行业参与者可以挑出稳定的对象、事件与字段，形成便于不同规模企业采用的规则，并保留修订与提出异议的途径。

共同规则的价值，还取决于新参与者能否承担接入和维护成本，旧系统能否逐步适配，以及规则是否允许不同业务说明自己的条件。采用 Agent 的企业数量增加，不等于这些条件自然成熟。行业组织、主要企业和较小参与者都需要进入讨论，避免共同接口只服务一种经营方式。

更广泛的协作有机会减少反复解释，让经验跨越企业边界。但它也把问题推进了一步：是谁贡献知识、承担新的工作，又是谁得到收益？下一章从任务与学习出发，讨论这些变化对劳动和价值创造意味着什么。

## 第 14 章 知识、劳动与价值创造的新可能

### 先看工作由哪些任务组成

一位项目协调人员的工作，可能包括寻找资料、整理进展、核实冲突、促成讨论和处理临时变化。Agent 能帮助完成其中一些任务，并不意味着剩余工作会按相同比例减少。资料整理更快之后，需要协调的项目可能更多，也可能更早发现原先没有看见的问题。

因此，讨论工作变化，可以先把岗位拆成任务，再看任务之间的关系。哪些已经能在明确条件下交给 Agent，哪些需要人核实，哪些依赖关系、经验与责任？本章据此前进，以下关于岗位与分配的情景均为条件推演，不是已经发生的普遍结果。

国际劳工组织的[《生成式 AI 与就业：2025 年更新》](https://www.ilo.org/publications/generative-ai-and-jobs-2025-update)从职业任务出发评估潜在暴露，并讨论任务改变与人类投入。这样的研究帮助我们辨认工作可能怎样变化；职业暴露不能直接解释为已经发生的就业减少、工资变化或社会收益。

### 更容易获得答案之后，怎样学会判断

新人过去遇到一个术语，可能需要问同事、翻旧文件，再找到具体案例。知识经过共建后，Agent 有机会把解释、来源和适用例子一起带到任务中。获取帮助的门槛由此可能降低，学习也可以更贴近手头的问题。

但看到一份好答案，与能够判断答案是否适用，仍然是两件事。新人如果只负责转交生成结果，可能绕过形成理解所需的比较和纠错。等到材料不完整、情况改变时，就不容易知道该追问什么。

团队可以把一部分节省出的整理时间用于学习：让新人先解释一处冲突，再对照 Agent 的分析；请有经验的人说明为什么在这里停下来确认；保留从材料到结论的路径。使用者逐渐能够提出更好的问题，才表明知识正在变成自己的能力。

日常认知也提出了值得观察的问题：如果总让 Agent 先给结论，我们是否会过早沿着它的表达继续思考？可以尝试先提出自己的问题，再要求比较不同解释、检查关键依据，看看是否能发现此前忽略的条件。这是可供检验的学习安排，也需要组织给讨论和练习留出时间。

### 经验成为共同知识，也需要新的劳动

一位熟悉业务的员工，可能很快看出一张表中的异常。把这份经验写成别人和 Agent 能采用的知识，需要补充条件、反例和判断依据，有时还需要承认哪些部分目前说不清。经验转移是一项工作，需要投入与核实。

这项工作有机会让更多人少走弯路，也可能使贡献者长期承担额外答疑。管理者可以把知识贡献、核实和维护纳入分工，安排参与时间，记录贡献，并在方法被广泛采用时重新商定支持职责。这样，共享知识才有持续来源。

经验本身也会改变。过去有价值的是记住许多细节，资料获取方便之后，价值可能更多体现在辨别例外、提出问题和理解取舍。不过，这仍取决于工作的内容。企业应观察哪些判断反复影响结果，再培养相应能力，不能仅凭一种工具出现就宣布某类经验已经过时。

### 岗位与管理可以围绕完整任务调整

当整理、查询和起草能够由人机共同完成，岗位可能承接更完整的任务。一位协调人员除了汇总进展，也可能跟踪异常到被解决；主管可以减少反复催报，把注意力放在跨团队的取舍上。这样的调整需要相应权限、训练和可承担的工作范围。

也存在另一种安排：同样人数处理更多事项，却没有减少交接，也没有增加学习和判断时间。员工表面上拥有了工具，实际工作可能更碎、核查压力更大。任务量上升是否构成改善，应结合质量、负担、成长和报酬一起判断。

管理者可以与员工共同重画一项任务：谁维护依据，谁处理异常，谁作出决定，忙不过来时怎样调整。评价从“产出了多少份材料”转向“解决了什么问题、留下什么可用知识”，才有机会让新能力支持工作质量。中间协调层是否变化，也应看这些职责怎样被承接，不能只按组织层级推断。

### 创造更多价值之后，谁得到什么

个人节省时间、企业增加价值和劳动者增加所得，是相互关联而又不同的结果。企业若减少返工、提高交付质量，可能获得更多可分配的收益；收益最终体现为工资、奖励、培训、服务改善还是资产所有者所得，需要具体安排。

下面几种情景用于辨认条件，可以在同一家组织同时出现，并非对未来的预测。

| 情景 | 可能的影响对象与结果 | 实现条件及可观察信号 |
| --- | --- | --- |
| 共同能力支持更完整的工作 | 员工学习与判断机会增加，客户获得较稳定的交付 | 留出学习时间、调整职责；观察独立处理能力与整体质量 |
| 新能力主要用于增加任务量 | 企业产出可能增加，员工投入和压力也可能增加 | 比较完整工时、返工、工作量与报酬，听取员工反馈 |
| 改善形成收益并有分享安排 | 劳动所得、培训机会或服务质量可能改善 | 确认实际收益与分配办法，观察参与者实际获得什么 |
| 能力与收益集中在少数参与者 | 资产价值或议价优势可能集中，其他人承担接入成本 | 比较不同规模参与者的成本、选择空间和持续参与情况 |

资产价值的变化还受到需求、竞争和其他条件影响，不能直接从技术能力推算财富增长。即使共同创造了更多价值，也不会自动得到某一种分配结果。把贡献与实际所得放在同一张讨论桌上，有助于参与者辨认改善应继续朝哪里推进。

### 把希望落实到能够参与的安排中

员工可以记录任务怎样改变，提出需要保留的学习机会，贡献可核实的经验，也说明增加了哪些负担。管理者可以让员工参与任务设计，把核查与维护纳入工时，并将实际改善与成长、奖励和工作安排联系起来。

企业和合作伙伴可以共同检验收益与成本落在哪里，为较弱的参与者提供采用条件；行业层面的交流可以扩大可用知识，让更多人参与规则讨论。不同主体推动的改变会相互影响，积极的结果需要在一次次具体安排中形成。

当人能够获得更好的知识、承担更有意义的任务，并对成果和时间有更多参与权，工作改善才逐渐接近生活中的感受。省下的时间怎样使用，哪些事务愿意委托，哪些判断希望亲自保留？下一章从这些问题出发，把本书的讨论带向智能生活。

## 第 15 章 从智能工作走向智能生活

### 效率改善之后，时间会去哪里

设想一位工作者已经能够和 Agent 配合：资料更容易找到，周报中的冲突能够及时看见，一些重复整理也有了可以沿用的方法。接下来，他面对的选择可能是多接几项任务，也可能是把更多时间放到判断、沟通和学习上。

工具并不替他决定时间的去向。团队怎样安排工作、怎样评价贡献，以及个人能否对安排提出意见，都会影响这种改善最后留下什么。讨论智能工作，走到这里就需要讨论人的选择。

如果把原来反复核对的时间转给需求理解，交付可能更接近使用者真正需要的东西；如果把它用于向同事解释判断依据，共同知识可能更扎实；如果只是增加更多相互等待的报告，原有瓶颈也可能换一种形式回来。可以从这些具体变化中，判断一种新方法是否值得继续。

### 让新增能力增加人的选择

本书所期待的积极变化，是人更容易获得相关知识，更有条件理解问题、形成判断和协调行动。这种期待需要通过实际安排实现。

对新人而言，可以从一份有来源的项目说明入手，沿着记录了解术语、流程和曾经的取舍，再带着自己的问题请教同事。对经验丰富的人而言，可以把容易口头遗漏的判断写清楚，让别人理解为什么某些情况需要例外处理。两者都有机会把更多注意力放在具体问题上。

与此同时，还要留下独立练习的空间。如果一个人每次都拿到整理好的答案，却没有机会核对来源、比较方案和解释理由，完成任务与理解工作之间就可能出现距离。安排一次自己复核的任务、一次向同事讲清判断的讨论，都是可以尝试的办法。

能力的增长可以体现在更多选择上：更清楚自己要做什么，能询问更具体的问题，也更有把握决定什么时候接受建议、什么时候继续查证。这样的变化，比工具使用次数更接近个人长期的发展。

### 从自己的位置参与改变

普通工作者可以从一项可检查的任务开始，保留材料、成果和判断，把一次有用经验整理成同事可以试用的说明。遇到不适用的地方，如实指出，让共同方法继续修正。

团队负责人可以选择一处反复发生的交接问题，和执行者一起澄清信息、责任与完成标准。为知识维护安排时间，为提出错误和例外留出渠道，再观察整个流程是否改善。员工的反馈在这里是设计依据。

企业与集团的管理者可以把知识、工具和流程投入放在同一项业务目标下讨论。哪些能力值得共同建设，哪些需要保留业务差异，节省的资源怎样重新安排，员工怎样获得学习机会，都可以进入明确的决策。

行业参与者则可以从共同术语和一段具体协作开始。例如，合作方怎样理解订单变更、怎样确认状态、怎样处理例外。先让双方能够可靠地接续工作，再谈更大范围的互通。

这些行动相互关联。个人贡献知识，需要组织允许他投入时间；企业推广方法，需要业务人员愿意反馈真实问题；跨企业协同，需要各方认可合作的意义。每个层次都有人能够推动其中的一部分。

### 让工作的改善回到人的处境

讨论工作方式变化，也应该听到承担工作的人怎样描述变化。重复劳动是否减少了，临时打断是否更少了，职责是否更清楚了，提出不同意见是否更容易了？这些问题能够补充效率指标。

知识共建尤其需要认真处理贡献。如果团队期待员工整理经验，却仍然只按即时交付量评价他们，共建就容易变成工作之外的额外负担。把维护时间、帮助同事和修正错误纳入可见的贡献，更有可能形成持续参与的条件。

对收益的安排也应当具体。组织可以讨论如何把新的能力用于更好的服务、员工训练、改善工作节奏或增加承担复杂任务的机会。采用哪种安排，需要结合业务和参与者的意见；工具本身没有替这些选择提供唯一答案。

这也是组织智能值得追求的一个方向：让更多人理解工作怎样发生，并有条件参与改进。技术能力与人的成长能够相互支持，需要在制度和日常协作中不断落实。

### 把协作经验带回日常生活

从智能工作走向智能生活，可以先沿用已经熟悉的方法：说明想达到什么结果，准备相关信息，约定谁作决定，再检查实际成果。

用一个生活中的说明情境来看：家人希望一起安排一段假期。Agent 可以协助整理各自已经说明的空闲时间、必须保留的安排和待讨论事项，再提出几个可比较的方案。每个人仍然需要表达自己的偏好，彼此协商，最后共同决定。帮助整理信息的能力，服务于这些具体的人。

另一个情境是成人学习。一个人想理解某个领域，可以让 Agent 帮助整理问题、寻找有出处的材料、比较不同解释，然后自己阅读、练习和复述。是否真正理解，要通过能够说明理由、迁移方法和发现问题来判断。工作中的来源意识和复盘习惯，在这里仍然有用。

生活还会提出新的问题。哪些信息愿意分享，哪些安排需要征求他人意见，哪些事情值得自己慢慢完成，需要在具体关系中重新约定。工作中能够访问的资料，也不能自然延伸为生活场景可使用的材料。

### 为智能生活留下一个起点

下一本《智能生活》（Agent），将沿着这些问题继续展开：日常事务、学习、家庭与公共参与怎样借助新的能力，人又怎样保留判断、关系和自主安排生活的空间。

回到本书的起点，一份周报能帮助我们看清一项工作；共同知识与工具能够支持一群人协作；更大范围的流程、激励和合作安排，则影响这些能力最终带来什么。

个人可以从一项任务开始，组织可以从一段协作开始。让成果有依据，让知识有人维护，让责任能够接续，再让参与者看见并影响改变。新的工作范式，就在这些可以采取、可以检查、可以修正的行动中逐步形成。

## 附录 A 五份可以改写使用的工作模板

以下模板是本书提出的实践工具。先按当前任务和组织条件删减，不必为了填满表格增加工作。

### 任务委托单

| 项目 | 要说明什么 |
| --- | --- |
| 目标与使用者 | 成果将支持谁作什么决定或完成什么工作 |
| 输入与时点 | 使用哪些资料、版本和统计截止时间 |
| 规则与缺失 | 按什么口径判断，缺失与冲突怎样处理 |
| 能力与动作 | 可以查询、计算、生成或修改哪些内容，哪些决定由人作出 |
| 交付与验收 | 保存什么成果、附哪些依据，怎样判断已完成 |

## 附录 B 术语与进一步阅读

### 本书采用的几个术语

**Agent**：围绕目标，借助可用工具选择和推进若干步骤的 AI 系统。本书关注可以观察的任务与交付，不仅根据产品名称判断能力。

**上下文**：当前任务中可供使用的相关信息，包括目标、资料、规则、状态、工具说明和执行中取得的信息等。

**企业知识基座**：组织共同维护并能按范围使用的事实、规则、经验与来源，包含更新和纠错的安排。

**企业大脑**：本书用于描述知识、业务情境、模型、系统工具和人的判断相互配合的比喻；并非所有产品共有的统一定义。

**工具能力**：通过可用系统与接口实现查询、计算、提交或状态更新等动作的能力。工具说明帮助理解和选择，实际执行仍依赖运行条件。

**组织效能**：本书综合讨论目标达成、交付质量、整体周期、资源投入与协作体验，不以一个人的生成速度代替。
